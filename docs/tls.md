# TLS transport and certificate trust

The `tls` diagnostic runs RDP security negotiation and upgrades the same TCP
connection to TLS. It stops before CredSSP/NLA or any session setup. The
negotiation offer describes modes the diagnostic can inspect, not completed
authentication implementations.

## Trust policy

- Use rustls 0.23 and ring; standard CA/SAN verification is the default.
- Enable TLS 1.2 and TLS 1.3; do not fall back to legacy RDP security or old TLS.
- Disable TLS session resumption as required by MS-CSSP section 3.1.5.
- Load platform roots through rustls-native-certs by default. Its
  `SSL_CERT_FILE` and `SSL_CERT_DIR` environment overrides apply.
- An explicit `--ca <pem-file>` replaces platform roots for this invocation.
  Empty, unreadable or malformed certificate files fail before network access.
- Verify the chain, certificate validity and the supplied DNS name or IP SAN.
  Connecting by IP requires that IP in the certificate's subject alternative
  names; reverse DNS is not used to change the expected identity.
- Alternatively, `--cert-sha256 <fingerprint>` explicitly trusts one exact leaf
  certificate for that invocation's destination. This replaces CA and SAN
  validation, while still checking certificate parsing, validity and TLS
  handshake signatures. It cannot be combined with `--ca`.
- Never disable verification or automatically trust certificates received over
  an unauthenticated connection. No credentials are accepted by this command.

A self-signed certificate may be supplied as an explicit trust anchor if it
satisfies the verifier's certificate requirements. Not every autogenerated
RDP certificate is guaranteed compatible. A private CA and a correctly named
server certificate provide a straightforward test setup.

The explicit pin accepts 64 hex digits or 32 consistently colon/hyphen-separated
hex bytes, case-insensitively. A missing, malformed or mismatched pin fails;
there is no fallback to another trust mode. The verifier is bound to the supplied
destination name/IP and TLS resumption remains disabled. No trust is saved.
The CLI reports pin-based trust separately from CA/name verification.

Pinning is intended for explicitly approved certificates such as Windows RDP
certificates without SANs. Obtain or confirm the fingerprint through a trusted
channel. Selecting a fingerprint first observed over the network is a user trust
decision, not independent confirmation of the host's identity. Pins must be
reselected explicitly after certificate rotation. Pin mode does not validate
the issuer chain, certificate self-signature, SAN, EKU or revocation policy;
the exact certificate and proof of private-key possession are the trust basis.

This currently uses PEM or per-invocation pin-based trust. A graphical certificate
review flow, persistent per-host trust and certificate rotation handling are
future work. No CRL distribution-point fetching or online OCSP/revocation
checking is implemented. System trust roots do not imply full platform
certificate-policy parity.

## Deadlines

TCP connects share five seconds across resolved addresses. RDP response reads
have another five-second deadline. TLS has a separate five-second deadline,
checked before every socket read/write so partial records cannot continually
reset the timeout. System DNS and local trust-file loading are outside these
network deadlines.

## Validation

Synthetic loopback tests cover TLS 1.2/1.3, DNS and IP SAN validation, untrusted
issuers, wrong names, expired certificates and a nonresponsive peer. Executable
tests perform RDP negotiation followed by TLS on one socket, check explicit
PEM/pin trust and verify failure exit codes. Pin tests include SAN-less leaves,
wrong pins, expired/not-yet-valid certificates, destination changes and wrong
private keys for both TLS 1.2 and TLS 1.3. Fixture keys exist only in memory;
temporary files contain public certificates and are removed after tests.

These fixtures are not evidence of Windows, xrdp or GNOME interoperability.
The [first Windows host check](windows-first-probe.md) passed negotiation and
TLS 1.3 using an explicitly selected certificate pin. System trust rejected the
issuer. The user chose the previously observed certificate for the pin without
independent host-side confirmation; see the report for the exact trust basis.
